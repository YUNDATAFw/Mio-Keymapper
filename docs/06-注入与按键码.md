## 6.1 输入模型与注入器选择

脚本问 `MioEngFun.getInputModel()` 得到当前注入模式（`InputModelManager`）：

| 值 | 常量名 | 注入通道 |
|---|---|---|
| `0` | `MODEL_IME` | Mio 内置输入法 |
| `1` | `MODEL_SHIZUKU` | Shizuku（root / ADB 授权） |
| `2` | `MODEL_GAMEPAD` | 虚拟手柄（uinput） |
| `-1` | `MODEL_NONE` | 无可注入通道 |

宿主在决定「谁来做按键注入」时：

- 读取用户存储的模型配置（`APP_CONFIG_INPUT_MODEL`），缺省按 `MODEL_IME`。
- `MODEL_SHIZUKU` 且 Shizuku 可用 → 走 Shizuku；否则走 IME；结果缓存 3 秒。
- 没有任何可用注入器时，动作类函数返回 `false`（**不抛错**）。

各就绪查询的语义：

| 函数 | 成立条件 |
|---|---|
| `isImeReady()` | IME 已启用、已设为当前输入法、运行中且输入连接建立 |
| `isShizukuReady()` | Shizuku 已授权可用 |
| `isMapReady()` | 同一 Shizuku 通道可用（历史命名） |
| `isGamepadReady()` | 虚拟手柄已开启 |
| `isSensorReady()` | 旋转传感器可用（与注入无关，见 [04 §3](04-模块API速查.md)） |
| `isEngineReady()` | 注入器可用 **或** 手柄已开启 |

### 守卫模式（每个 `onTriggerDown` 的第一步）

```java
export fn Void onTriggerDown() {
    // ① 通道守卫：没有通道时给提示并退出，不进循环
    if(!MioEngFun.isEngineReady()) {
        MioEngFun.showToast("按键注入未就绪，请先开启输入法或Shizuku")
        return
    }

    while(MioEngFun.isTriggerDown(ACTION_ID)) {
        // ② 每次注入都检查返回值：false = 真失败，立即停
        Bool ok = MioEngFun.tap("KEYCODE_Q", 5)
        if(!ok) {
            MioEngFun.showToast("按键注入失败，已停止")
            return
        }
        MioEngFun.sleep(25)
        if(MioEngFun.isTriggerUp(ACTION_ID)) break
    }
}
```

> 通道可能**中途断掉**（用户切走输入法、Shizuku 授权失效），所以守卫要写在循环里（②），不能只在开头查一次。

### 手柄通道要单独守卫

`MioGamepad.*` 走 uinput，与 `isEngineReady()` 的判定不完全重合——用前检查 `isGamepadReady()`（[§6.5](#65-手柄按钮miogamepad)）。

## 6.2 按键名（`KeyMapping` 总表）

所有 `tap/keyDown/keyUp/tapGroup/tapCombo` 都接受**按键名**，合法名共约 141 个，全部为 Android `KeyEvent` 的 `KEYCODE_*` 名称，另有手柄别名。大小写需与下表完全一致；`isKeyValid(name)` 即按此表校验（未知名返回 `false`，注入函数对未知名抛「未知按键名」）。

### 字母与数字

`KEYCODE_A` ~ `KEYCODE_Z`（26 个）；`KEYCODE_0` ~ `KEYCODE_9`（10 个）。

### 修饰键（常配合 tapCombo/tapGroup 做组合键）

`KEYCODE_ALT_LEFT` / `KEYCODE_ALT_RIGHT` / `KEYCODE_CTRL_LEFT` / `KEYCODE_CTRL_RIGHT` / `KEYCODE_SHIFT_LEFT` / `KEYCODE_SHIFT_RIGHT` / `KEYCODE_META_LEFT` / `KEYCODE_META_RIGHT` / `KEYCODE_SYM` / `KEYCODE_FUNCTION` / `KEYCODE_CAPS_LOCK` / `KEYCODE_NUM_LOCK` / `KEYCODE_SCROLL_LOCK`

### 系统与导航

`KEYCODE_HOME` / `KEYCODE_BACK` / `KEYCODE_CALL` / `KEYCODE_ENDCALL` / `KEYCODE_VOLUME_UP` / `KEYCODE_VOLUME_DOWN` / `KEYCODE_POWER` / `KEYCODE_CAMERA` / `KEYCODE_MENU` / `KEYCODE_SEARCH` / `KEYCODE_PAGE_UP` / `KEYCODE_PAGE_DOWN` / `KEYCODE_ESCAPE` / `KEYCODE_DPAD_UP|DOWN|LEFT|RIGHT|CENTER` / `KEYCODE_TAB` / `KEYCODE_ENTER` / `KEYCODE_DEL` / `KEYCODE_CLEAR` / `KEYCODE_BREAK` / `KEYCODE_INSERT` / `KEYCODE_MOVE_HOME` / `KEYCODE_MOVE_END` / `KEYCODE_EXPLORER` / `KEYCODE_ENVELOPE`

### 功能键

`KEYCODE_F1` ~ `KEYCODE_F12`。

### 小键盘

`KEYCODE_NUMPAD_0` ~ `KEYCODE_NUMPAD_9` / `KEYCODE_NUMPAD_DIVIDE` / `KEYCODE_NUMPAD_MULTIPLY` / `KEYCODE_NUMPAD_SUBTRACT` / `KEYCODE_NUMPAD_ADD` / `KEYCODE_NUMPAD_DOT` / `KEYCODE_NUMPAD_COMMA` / `KEYCODE_NUMPAD_ENTER` / `KEYCODE_NUMPAD_EQUALS`

### 符号与媒体

`KEYCODE_STAR` / `KEYCODE_POUND` / `KEYCODE_COMMA` / `KEYCODE_PERIOD` / `KEYCODE_SPACE` / `KEYCODE_AT` / `KEYCODE_SLASH` / `KEYCODE_BACKSLASH` / `KEYCODE_EQUALS` / `KEYCODE_MINUS` / `KEYCODE_SEMICOLON` / `KEYCODE_APOSTROPHE` / `KEYCODE_LEFT_BRACKET` / `KEYCODE_RIGHT_BRACKET` / `KEYCODE_GRAVE`（数值 68）/ `KEYCODE_MEDIA_PLAY_PAUSE` / `KEYCODE_MEDIA_STOP` / `KEYCODE_MEDIA_NEXT` / `KEYCODE_MEDIA_PREVIOUS`

### 手柄别名（`GAMEPAD_*`，供按键注入复用）

`GAMEPAD_A`(B·A) / `GAMEPAD_B` / `GAMEPAD_X` / `GAMEPAD_Y` / `GAMEPAD_L1` / `GAMEPAD_R1` / `GAMEPAD_L2` / `GAMEPAD_R2` / `GAMEPAD_SELECT` / `GAMEPAD_START` / `GAMEPAD_LS` / `GAMEPAD_RS` / `GAMEPAD_DPAD_UP|DOWN|LEFT|RIGHT`

> `KEYCODE_Z` 在表中出现两次（冗余），仍以一次为准。

## 6.3 注入函数行为细节

| 函数 | 行为 |
|---|---|
| `keyDown(name)` | 注入按下，**不自动松开**；需对应 `keyUp` 配对，适合按住型操作 |
| `keyUp(name)` | 注入松开 |
| `tap(name, pressMs)` | 按下 → `Thread.sleep(pressMs)`（`>0` 才 sleep）→ 松开 |
| `tapGroup(names, pressMs)` | 按下列表内全部键 → 保持 `pressMs` → **逆序**松开；中途异常也会尽力逆序补松 |
| `tapCombo(主键, 组合键, primaryKeepMs, comboKeepMs)` | 按住主键 → 按下组合键 → 保持 `comboKeepMs` → 松组合键 → 再保持 `primaryKeepMs` → 松主键（典型如 `Ctrl+C`） |
| `inputText(content)` | 注入一串文本 |

任一步注入抛 `InjectionException` 或线程被中断 → 返回 `false`，且尽可能恢复（松开已按下的键）。

### 参数怎么选（经验参考）

| 参数 | 太小 | 太大 | 实用起点 |
|---|---|---|---|
| `tap` 的 `pressMs` | 游戏吃不到（<5ms 部分游戏丢事件） | 手感拖沓、连发频率低 | 点按类 `5~20`；指令回车 `20` |
| 循环 `sleep` | 空转耗电、日志刷屏 | 反应迟钝 | 连发 `10~25`；节拍类按游戏攻速调 |
| `tapCombo` 的 `comboKeepMs` | 组合键丢失 | 组合键重复触发 | `20~50` |
| `tapCombo` 的 `primaryKeepMs` | 主键提前松开、组合失败 | 无害但占时 | `30~80` |
| `keyDown` 持续时长 | — | — | 由 `while(isTriggerDown)` 决定，无固定值 |

通道差异提示：

- **IME 通道**：`inputText` 依赖输入法，逐字上屏有额外延迟——指令发送前后要留 `sleep`（参考 [07 §7.5](07-从零写示例.md) 的三段时序，且都做成了可配置）。
- **Shizuku 通道**：注入直达、延迟低，但部分应用对全局注入有防护，表现为 `tap` 返回 `true` 却无效果——用「游戏内实际反应」验证，别只信返回值。
- **Gamepad 通道**：走 `MioGamepad.*` 的语义（摇杆/按钮），与 `tap` 的键盘语义不同——同一游戏两套键位别混用。

> 所有数值都建议**暴露到配置页**（[11](11-配置页与HostData.md)）让玩家自己调——机型、系统、游戏版本都会影响合适值。

## 6.4 常用组合键示例

```java
// Ctrl+C（慢速稳妥版）
MioEngFun.tapCombo("KEYCODE_CTRL_LEFT", "KEYCODE_C", 50, 30)

// Alt+F4 式组合
MioEngFun.tapGroup(["KEYCODE_ALT_LEFT", "KEYCODE_F4"], 30)

// 按住 W 移动 200ms 再松开
MioEngFun.keyDown("KEYCODE_W")
MioEngFun.sleep(200)
MioEngFun.keyUp("KEYCODE_W")
```

## 6.5 手柄按钮（MioGamepad）

`MioGamepad.pressButton / releaseButton` 的 `button` 参数大写，取值：

`A` `B` `X` `Y` `LB` `RB` `LT` `RT` `SELECT` `START` `LS` `RS`
及十字键 `DPAD_UP` `DPAD_DOWN` `DPAD_LEFT` `DPAD_RIGHT`

（也接受 `GAMEPAD_A` 形式；未知名仅记录日志、不抛错，脚本若在意可先 `isKeyValid`/`isGamepadReady` 判断。）

## 6.6 排障

| 现象 | 检查 |
|---|---|
| 所有 `tap` 都返回 `false` | `isEngineReady()` / `getInputModel()`——无通道或 `-1`；先让用户启用 IME 或授权 Shizuku |
| 只有手柄函数不生效 | `isGamepadReady()` 是否为 true（虚拟手柄没开）；`isEngineReady()` 为 true 不代表手柄可用 |
| `未知按键名 xxx` | 拼写/大小写；对照 §6.2 表（全大写 `KEYCODE_*`）；或先 `isKeyValid(name)` |
| 注入到了错误的应用 | 注入是全局按键事件，焦点在哪个应用就发给哪个——先让目标应用持有焦点 |
| 输入法通道时灵时不灵 | 用户可能切走了 Mio 输入法；`isImeReady()` 每次用前重查 |
| 组合键没生效 | 用 `tapCombo`（有时序保证）而非手写两次 `tap`；`tapGroup` 是**同时按下再逆序松开** |
| 注入后按键没松开 | `keyDown` 必须配对 `keyUp`；异常路径在 `tap/tapGroup` 内会尽力补松，手写 `keyDown` 要自己保证收尾 |

宿主日志关键字：`MioEngFunBridge`、`InputModelManager`、`ShizukuKeyInjector`。
